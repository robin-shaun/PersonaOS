# PersonaOS v0.1 记忆连续性演示

这条演示只证明首个公开纵向切片：同一 Persona 的 UUID、已确认记忆和来源证据
可以跨进程重启保持，并可迁移到使用另一数据库和加密密钥的干净环境。默认流程
不调用外部模型。

## 30～60 秒录屏脚本

录屏前按 README 启动 Compose、创建账户，并用“载入虚构演示人物”确认至少一条
记忆。将浏览器停在“人物总览”，终端停在仓库根目录。

1. **0～8 秒**：展示人物名称与完整 Persona ID；进入“记忆”展开已确认内容和
   来源时间。
2. **8～20 秒**：在终端执行 `docker compose restart api worker web`，等待三个
   服务恢复健康。
3. **20～36 秒**：刷新浏览器，指出 Persona ID 没有变化；进入“问答”重复之前的
   问题。
4. **36～48 秒**：展开回答引用，展示原文件、摘录和行号，说明答案来自持久化
   记忆而不是当前聊天上下文。
5. **48～60 秒**：进入“审计与导出”，勾选原始资料并生成 JSON，展示导出清单
   的 SHA-256。

普通停止使用 `docker compose down`，不要加 `-v`；后者会永久删除本地数据卷。

## 在干净环境验证恢复

导出时必须勾选原始资料。目标环境先按 README 启动并创建管理员账户；空工作区
可以在 Web 欢迎页选择“从可校验导出恢复”。若已有其他 Persona，只要不存在相同
UUID，仍可执行 API 等价的命令行恢复：

```bash
.venv/bin/python examples/persona_restore.py \
  /可信路径/persona-export.json --username admin
```

密码通过无回显提示输入，不会进入 shell 历史。服务会先验证导出清单、规范 JSON
字节数、原始资料 SHA-256 和内部引用图，再用目标环境的新密钥重新加密资料。恢复
保留原 Persona UUID 和历史时间，将模型边界重置为 `local`，并重建本地向量。

若目标已经存在相同 UUID，恢复会返回冲突并保持现有数据不变；当前版本不提供
覆盖恢复，以避免误删或合并两个身份。

## 自动化证据

```bash
.venv/bin/python -m pytest tests/test_persona_portability.py -q
```

测试会使用两个独立 SQLite 数据库和两套 AES 密钥，验证导出、导入、容器重建、
重启后引用问答、不同 Persona 隔离，以及篡改包在写入前被拒绝。

## 当前限制

- 只接受 `persona-export-v1`，且完整恢复要求导出包含原始资料；
- 相同 Persona UUID 已存在时不会覆盖或合并；
- 目标账户成为恢复数据的新所有者，外部模型授权不会随导出迁移；
- 向量属于可派生数据，不携带旧向量数组，而是在目标环境按当前本地 embedding
  空间重建。
